## 2. 先预测，再执行

三类字段有不同职责：`id` 是内部标识，`vehicle_code` 等业务编号便于识别，外键记录实体之间的引用。

例如 `work_order.vehicle_id = 10`、`battery_id = 7`，而电池 7 属于车辆 20：只要车辆 10 和电池 7 都存在，普通外键就能通过。后续 Service 必须比较两边的 `vehicle_id`；并发下还需要事务等保护，不能把一次查询当成完整保障。

每个实验先回答“允许还是拒绝、谁负责拒绝”，再执行。提示后完成与首次独立回答分别记录，不把脚本产出等同于掌握。

## 3. 本机登录与建表

在自己的 PowerShell 中运行，密码只在终端的提示处输入，不放到命令参数、聊天、截图或仓库中：

```powershell
mysql --host=localhost --user=root --password --default-character-set=utf8mb4
```

进入 `mysql>` 后先执行只读查询：

```sql
SELECT VERSION() AS server_version;
SELECT SCHEMA_NAME FROM information_schema.SCHEMATA
WHERE SCHEMA_NAME = 'ebike_ai_day11';
```

要求确认是 MySQL 8.0.16 及以上的兼容版本；本实验针对 MySQL 8.0，不假定 MariaDB 或其他版本等价。MySQL 8.0.16 起才执行 CHECK 约束，旧版本会忽略。[官方说明](https://dev.mysql.com/blog-archive/mysql-8-0-16-introducing-check-constraint/)

如果第二条查询有结果，先停止创建，使用以下查询检查既有内容并与协作者核对；不自动重用、删库或覆盖：

```sql
SELECT TABLE_NAME, TABLE_TYPE FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'ebike_ai_day11';
```

确认目标库不存在后，打开 [建表脚本](../sql/day11/01_create_tables.sql)，**在 mysql 客户端逐条复制执行**，顺序为创建库、选择库、配置会话、车辆、电池、工单、结构检查。CREATE TABLE 要完整复制到分号，不能只执行其中一行。

- 任何错误都先停止，记录错误编号和语句位置；不跳过错误继续，不使用 `--force` 批量运行建表。
- 不推荐一次 `source` 整个建表文件：交互客户端的继续执行行为可能使前一步失败被忽略。
- 脚本故意没有 `IF NOT EXISTS`，避免把既有不兼容表伪装成创建成功。
- 建表中途失败时保留已成功的表，先用 `SHOW CREATE TABLE` 核查，再修复未完成部分；不要重跑整个文件或自动清库。
- MySQL DDL 会隐式提交，`ROLLBACK` 不能撤销建库、建表。本实验的数据回滚与 DDL 分开。[官方事务说明](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)

物理设计约定：

| 项目 | 本次决定 |
|---|---|
| 引擎和字符集 | InnoDB、utf8mb4；排序规则 utf8mb4_0900_as_cs，编号和状态区分大小写 |
| 主键、唯一键 | 自增 BIGINT UNSIGNED 内部主键；车辆、电池、工单业务编号分别唯一 |
| 时间 | DATETIME(6)；每次写入会话设置 UTC，系统时间默认 CURRENT_TIMESTAMP(6)，更新时维护 updated_at |
| 历史时间 | received_at、completed_at 未知时保留 NULL，不能用系统创建时间代替 |
| 规格 | DECIMAL(10,3)，未知为 NULL；只校验存储值非负，不表示电池安全或规格合理 |
| 删除 | 外键 ON DELETE RESTRICT、ON UPDATE RESTRICT，不级联清除维修历史 |
| 索引 | 沿用 Day 10 三张表候选索引；有相同最左前缀的联合索引服务外键，不重复添加单列索引 |
| 代码和文本 | CHECK 校验状态、来源、结果；普通空格空文本由 TRIM 检查，未来 API 仍须完整处理空白与文本校验 |

`CHECK` 对 NULL 的判断可能产生 UNKNOWN 而通过，因此“COMPLETED 必须有结果”显式写 `completion_outcome IS NOT NULL`。单独写一个结果枚举判断不能代替非空条件。

时间采用会话 UTC 的约定，并非 DATETIME 自动具有时区。后续应用连接也必须设置 UTC。输入精度及舍入的 API 校验留待接入时处理。

## 4. 逐组验证与结果记录

确认三张表创建成功且为空后，打开 [验证脚本](../sql/day11/02_verify_constraints.sql)。在同一个交互连接内按编号逐组执行，保留变量和事务上下文。

这是人工核对的 SQL 实验，不是 pytest 或自动断言器。不能用“脚本执行完了”或客户端退出码宣称全部通过。

- 第 00 组必须确认当前数据库正确、三张表的计数均为 0；否则停止。
- 预期拒绝也属于正确结果，必须核对具体错误号和对应约束，不能把其他 SQL 错误当成预期拒绝。
- 每个异常写操作前设置 SAVEPOINT，后面回滚至该点，防止某项意外通过污染后续用例。
- 出现任何非预期结果，立即 `ROLLBACK;` 并停止排查；不要继续执行到最后才判断。
- 数据验证期间不要执行 DDL、COMMIT 或开启另一段事务；最后 ROLLBACK 应使三张表都恢复为空。自增序号可以有间隔，不要求回到 1。
- 所有 LAB 编号、现象、时间均为虚构测试数据，不是 CASE-001，也不是维修安全结论。

| 组 | 验证内容 | 预期结果 | 实测 |

## 5. 边界与学习验收

本次没有 API、ORM、连接池或数据库迁移工具，也没有新增 Python 依赖。其余八张表在后续小目标实现。

以下约束明确没有实现：同车辆电池关联、流程状态转换、维修完成需复检、区分新建与历史导入时的完成时间和取消原因要求。后三者不能仅靠本次字段的 NULL 定义完整保证，不能据此宣布维修系统已闭环。`REPAIRED` / `PARTIAL` 的复检支撑仍需未来 Service 校验。

学习验收记录（引导完成不等于首次独立掌握）：

- 主键与唯一编号：起初认为 ID 不同就能插入重复业务编号，经讲解后正确判断两者都不同时可插入；主键用于稳定关联、业务编号用于展示的理由尚未单独完整复述。
- 外键边界：起初误认为外键能保证电池归属，后来虽判断“不拒绝”，却归因为电池可空；实际反例后能说明双方存在即可通过，应比较工单车辆与电池所属车辆。字段名进一步明确为 work_order.vehicle_id 和 battery.vehicle_id。
- NULL 与空白：能正确判断只保留 NOT NULL 时普通空格仍可保存，1048/3819 已反馈；NULL、0、空字符串三者的完整解释尚未独立复述。
- 状态与结果：正确判断 COMPLETED + UNRESOLVED 为合法搭配，并反馈实际查询符合预期。
- 事务：起初不知道为何回滚不删除表；解释提交和事务边界后，正确回答“第一辆车已提交、第二辆车在新事务中回滚，最终保留一辆”。DDL 隐式提交与自增间隔尚需继续巩固。
- CHECK 的 UNKNOWN、独立定位约束的完整表达：保留为下一次复习项，不标记已独立掌握。

# 第 29 天：匿名维修案例采集模板

目标：用同一套字段记录真实维修过程，保留未知信息及证据来源。先整理总计 3–5 条（含 CASE-001）；30–50 条为后续累积目标。

## 采集规则

- 不记录姓名、电话、车牌、详细地址；案例编号只在项目内使用。
- 客户描述、检查观察、仪器测量、维修师判断、AI 建议分别记录。
- 尚未询问写“待补充”；确定当时没有记录写“未记录”；JSON 用 `null`，并在 `missing_information` 中解释。不能用 0 或模拟数据填空。
- 每项信息注明来源及确认状态。维修师确认转述不等于取得原始测量记录。
- 历史案例没有 AI 参与时，不补造 AI 诊断或审核记录。
- 复检通过只支持实际检查过的功能，不扩大为整车安全或长期可靠性。

## 空白模板

| 项目 | 填写内容 | 来源与确认情况 |
|---|---|---|
| 案例编号、采集日期 | CASE-xxx；采集日期不是维修日期 | 采集者记录 |
| 维修日期、车辆、电池背景 | 只填实际知道的类型、规格及适用场景 | 铭牌／维修师／客户转述；未知注明 |
| 客户报告的故障 | 现象、触发条件、仍能正常工作的功能 | 客户描述，不先写最终故障 |
| 实际检查 | 每项检查对象、观察结果；未提供结果不写“正常” | 维修师或当时记录 |
| 实际测量 | 数值、单位、测点、仪器、条件、时间 | 无记录则留空，不强制存在 |
| 初步判断与依据 | 当时怀疑的问题、排除依据、不确定项 | 与最终判断分开 |
| 最终判断与依据 | 确认的故障；未确认的根因不推断 | 维修师确认范围 |
| 维修措施 | 实际操作、更换部件和已知规格 | 不把模型建议当作已执行 |
| 复检与遗留问题 | 实际方法、观察结果、未验证事项 | 不虚构次数、时长、长期效果 |
| 确认情况 | 谁确认、通过何种渠道、哪些字段仍未确认 | 未确认内容不能标记为已确认 |

结构化示例见 `data/repair_cases/CASE-001.json`；原始叙述依据见 [第 8 天维修流程](repair-workflow.md)。新增案例先人工核对，再进入检索语料。不要批量生成“真实案例”。

## CASE-001 走查结果

已确认的叙述来自用户转述，用户在 2026-10-14 表示提供内容均由父亲确认。现有材料能表达：灯和喇叭失效但仍可骑行 → 检查保险、线束插头、转换器 → 维修师判断转换器损坏 → 更换转换器并整理包扎接头 → 灯光、喇叭功能复检正常。

不能确认：各项检查的具体发现、具体诊断测量依据、车型及部件规格、损坏根因、维修日期、复检次数与持续时间、长期使用结果。电压数值明确未记录。

诊断回归的输入只保留故障描述与当时可知的检查信息；最终故障、维修措施及复检结果放在预期结果侧。检索语料必须排除被测案例及其衍生文档，避免答案泄漏。

## 学习验收

1. 为什么 `null` 和 `0V` 不等价？
2. 为什么“检查过保险”不能改写为“保险正常”？
3. 为什么更换转换器后灯光恢复，不能单凭这条记录证明转换器烧坏的根因？

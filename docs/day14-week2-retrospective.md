阅读 [Day 13 文档](day13-work-order-service.md)、[Service](../src/ebike_ai/services/work_order.py) 与 [Service 测试](../test_cases/test_work_order_service.py)，先预测每个分支，再对照实现。

```text
成功：创建独占连接（autocommit=False）
      → 查询车辆 → 如指定电池，查询并锁定电池、校验归属
      → 插入 RECEIVED 工单 → commit 正常返回 → close → 返回工单 ID

失败：车辆/电池不存在或归属不符 → 不插入 → 尝试 rollback、close → 业务错误
      查询或插入异常 → 尝试 rollback、close → 持久化错误
      commit 异常 → 尝试 rollback、close → 提交结果未知，不自动重建
      commit 成功但 close 失败 → 携带已保存 ID 的清理错误，不回滚或重建
```

各 Repository 共用 Service 提供的连接，不自行提交、回滚或关闭。回滚与关闭各自尝试，清理错误不覆盖主要错误。新建车辆再建单是课堂假设，当前 Service 只接受已有车辆。

## 3. 六道问题的学习证据

| 问题 | 用户回答与纠正 | 记录结论 |
|---|---|---|
| 谁管理事务 | 正确指出先提交的车辆会保留，后续工单失败不能实现整体撤销，应该由 Service 在各步骤成功后提交；讲解补充同连接与 Repository 不提前提交 | 本题独立判断正确，连接条件经补充 |
| 电池归属 | 独立比较 battery.vehicle_id 与建单 vehicle_id；跨车辆时拒绝且不执行 INSERT | 本题通过 |
| 查得到是否已提交 | 起初选择原连接验证；讲解后在“遗漏 commit、回滚关闭”的新场景中正确指出返回 ID 不能证明提交，新连接查不到会暴露问题 | 经讲解后复验通过 |
| commit 异常 | 正确识别服务端可能已经保存；不能只凭异常断定失败，重建有重复风险，应新开连接核对；讲解补充按原工单编号及内容核对 | 本题核心判断通过 |
| 假连接的能力 | 正确区分归属分支与真实 SQL、跨连接查询、锁等待；误将提交异常的错误映射也归为必须真实数据库，已解释可用假 commit 抛异常验证 | 部分正确；纠正项尚未独立复验 |
| 已提交数据如何清理 | 正确指出 rollback 无法撤销已提交数据，提出测试库和业务库分离；讲解补充同一测试库内也须精确标识并清理本次数据 | 核心判断正确；精确清理方案独立复述待完成 |

原连接能看到本事务未提交的插入；Service 返回 ID 本身也不是提交证据。成功返回后新开连接按编号查到预期内容，可验证本场景的跨连接可见性，但不等于验证了断电恢复、复制延迟或全部并发行为。

假连接的 commit 抛异常，可以验证代码是否产生 WorkOrderCommitUnknownError，不能证明真实服务器最终有没有提交。核对数据库仍失败时，结果保持未知；不换编号盲目重建。

## 4. 下一步真实建单验证方案（未执行）

沿用现有 db 标记与 --run-db 开关，不依赖模型服务，不修改表结构，不把原 Day 12 回滚 fixture 当成已提交数据的清理机制。

### 隔离、准备与核对

1. 仅在已有 ebike_ai_day11 练习库显式运行。写入前核对连接目标与 SELECT DATABASE()，并预检三表的 InnoDB、必要字段、唯一约束、外键、CHECK、UTC 和严格模式；不匹配即停止，不自动修表。数据库凭据只在本机配置，不写入文档或报告。
2. 每个用例生成随机运行标识，为车辆、电池、工单分配不超过 32 字符的唯一业务编号。写入前保存本用例完整编号清单，确认这些编号原本不存在；成功插入时再记录 ID。既有数据不能作为清理对象。
3. 准备车辆 A、B，以及分别属于两车的电池 X、Y。准备连接先提交本用例的基础数据并关闭；Service 使用自己新建的连接，否则看不到准备事务尚未提交的数据。
4. 每次 Service 返回或抛出预期错误后，另开连接按准确工单编号核对行数、关联、状态和业务字段，再关闭核对连接。不复用测试开始前已经建立快照的事务。

### 场景清单

| 场景 | 操作 | 预期及独立核对 |
|---|---|---|
| 无电池建单 | A，battery_id=None，新工单编号 | 返回 ID；新连接查到同 ID、vehicle_id=A、battery_id=NULL、status=RECEIVED，完工字段为空 |
| 同车电池建单 | A 与属于 A 的 X，新工单编号 | 新连接查到正确车辆、电池和输入内容，恰好一条 |
| 车辆不存在 | 使用本库不可能存在的负数车辆 ID | VehicleNotFoundError；新连接按本次工单编号查不到记录 |
| 电池不存在 | A 与不可能存在的负数电池 ID | BatteryNotFoundError；没有本次工单 |
| 跨车辆电池 | A 与属于 B 的 Y | BatteryVehicleMismatchError；没有本次工单 |
| 重复工单编号 | 先成功建一单，再用同一编号再次调用 | 当前 Service 转为 WorkOrderPersistenceError；新连接确认只有原来一条，ID 和内容不变，不误记为专用重复编号错误 |

每个失败场景中“查询不到记录”仅证明该用例没有留下工单，单独不能证明从未尝试 INSERT；是否调用 INSERT 由现有假连接测试验证。上述成功查询验证提交后的可见性，不包含真实并发锁实验；FOR UPDATE 的真实等待效果另行设计有界并发测试。

### 清理已提交数据

- 无论准备、调用还是断言失败，都进入清理流程；先回滚并关闭仍打开的未提交连接，释放锁。
- 新建清理连接，再次核对目标库。按本用例准确编号查出记录，核对已知 ID 和归属；若提交响应丢失、没有返回 ID，则用写入前保存的唯一编号及预期内容核对。出现不匹配时停止删除并报告。
- 在一个清理事务中，按本次记录的准确 ID 与编号，依次删除工单、再电池、再车辆，最后提交。查询与删除使用参数化 SQL；不清空表，不按宽泛前缀批量删除，不禁用外键。
- 新开连接确认本用例编号均无残留。清理失败须保留主失败并单独报告残留的测试编号；不能以“执行过 rollback”冒充清理成功，也不能扩大删除范围。意外进程中断后的恢复依据本次运行清单处理。
